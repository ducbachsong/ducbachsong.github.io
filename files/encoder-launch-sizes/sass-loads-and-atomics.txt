The loads and atomics of the encoder kernels, from the test of commit e84ce51 built on Google Colab
(Tesla T4) with the command in the post (no -arch flag):

    cuobjdump -lelf test_encoder
    cuobjdump -sass test_encoder | grep -E "Function|LDG|RED|ATOM"

LDG.E.128 is a 16-byte (float4) load, LDG.E without .128 a 4-byte one. RED is an atomic add whose result
is not used: the thread sends it and does not wait. The program holds machine code for sm_75, the T4,
so nothing is compiled when it starts.

Read per kernel, one job of the loop:
  encoder_backward_wte_float_kernel  the token id and 4 bytes of encoded_grad, asked for together; one RED
  encoder_backward_wte_kernel        the token id and 16 bytes of encoded_grad, asked for together; four RED
  encoder_backward_wpe_kernel        four 16-byte loads of encoded_grad back to back (the loop over b,
                                     unrolled by 4); the remainder loop and the old float4 of wpe_grad after
  encoder_forward_kernel             the token id alone; when it is back, 16 bytes of wte and 16 of wpe together
